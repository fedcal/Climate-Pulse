<objective>
Deliver the three "metadata" router groups in a single coordinated plan: `/v1/stations` + `/v1/stations/{id}` (API-01, API-02), `/v1/meta/variables` (API-05, D-API-18, D-API-19), and `/v1/sources` + `/v1/sources/status` (API-04, D-API-13, D-API-14). They share the same Pydantic + asyncpg patterns, the same dependency-injection layer, the same cursor pagination contract (cursor is only consumed by `/v1/stations` in this plan; `/v1/observations` adopts it in plan 02-04), and the same RFC 7807 error contract delivered in plan 02-01.

Purpose: After this plan a Phase 3 dashboard generator could already prototype the map + variable-selector + source-health page against a stable OpenAPI surface — three quarters of the read API is live, and the resolution-resolver-heavy `/v1/observations` (plan 02-04) is the only remaining read path.

Output: Three router modules, three schema modules, two query modules, a shared `deps.py`, and main.py wiring that includes the three routers after the existing health router. API-11 (per-row provenance + quality flag exposure in responses) is partially delivered here (sources carry license + attribution in responses; observations get full provenance in plan 02-04).

Vertical MVP framing: After this plan a real user can (1) discover what stations exist with bbox filtering, (2) drill into one station's metadata + coverage window, (3) browse the variable catalog (so they know what to query next), (4) see which sources are healthy NOW. That is a complete "discovery" capability shipped end-to-end, parallel-prep for "query" (plan 02-04) and "export" (plan 02-05).

- (METAR comes in Phase 4 — out of scope here.)
Hardcode this map in `routers/sources.py` as `_SOURCE_CADENCE = {...}` with comments; per D-API-13 it can become env-configurable later but Phase 2 ships the documented defaults.
